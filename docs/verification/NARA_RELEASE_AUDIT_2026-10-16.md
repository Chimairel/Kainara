## Proposed online isolation and promotion

1. Keep localhost for repeated development/provider-stub/load tests.
2. Use a **staging Neon project + Railway API + Vercel frontend**, with an explicit `codex/staging` release branch and disposable or appropriately sanitized test records. Merely adding a database without separating its backend does not isolate testing.
3. Use a separate **presentation Neon project + Railway API + Vercel frontend**, following the existing `demo` branch. Preserve the current live environment until an authorized cutover and validated rollback exist. Two new branches are unnecessary because `demo` already exists.
4. Promote the same tested source tree, reviewed migrations and intentional reference data. Never promote test activity by overwriting presentation records with the staging/local database. The local copy is older and is not a current live backup. A copy of live data must preserve encryption keys, account relationships and post-backup activity; plan a bounded export/cutover before reading the nearly exhausted source project again.
5. Keep staging email/payment delivery and scheduled workers explicitly controlled. Confirm scheduler target and background worker lifecycle so online testing cannot send unintended messages or operate on presentation. Do not duplicate secrets wholesale: separate signing/session/scheduler credentials where appropriate, retaining the document encryption key when restoring encrypted documents.
6. Each environment's API must point only to its own database, frontend proxy and allowed origins. Add the new exact frontend origin to the Google OAuth client before testing Google login. Owner action may be required in Google Cloud Console; provide the URLs after provisioning. Any actual hosting-plan/billing gate must be handled explicitly.
7. Neon documents public network transfer allowances per project, shared across products within that project. Extra branches in one project do not provide an independent transfer budget. See [Neon plans](https://neon.com/docs/introduction/plans). New PostgreSQL projects do **not** add Gemini quota: local, staging and presentation using one Google project still share that provider limit, while their separate SQL admission ledgers cannot coordinate it.
8. At the authorized release, compare applied migration names/checksums and required flags on the exact target; preserve existing differences honestly. Activate Nara after the receipt table exists, finish both deployments, then perform bounded authenticated checks for chat, consent/recovery, credits, groceries, existing swap, RND/member questions and account security. Record actual host commits, worker/scheduler configuration and remaining limitations. Keep presentation testing bounded rather than promising that a new project fixes existing inefficient queries or external outages.

**Current status:** application audit complete within the stated evidence boundaries; two corrections implemented locally. Demo promotion, fresh hosted schema/behavior verification and the proposed environment creation/cutover remain separate work. No zero-regression guarantee is claimed.
