## Remaining presentation risks

These paths were identified by code inspection or existing runtime evidence. They are not presented as new browser reproductions.

1. **Provider availability and capacity.** Gemini can return overload/quota failures. Saved candidates and deferred jobs are retained; fresh generation can still be delayed. Existing earlier checks did not establish successful end-to-end generation of an entire fresh AI-backed week during provider overload. Keep a prepared synthetic plan available and perform a provider preflight before demonstrating new generation.
2. **Interrupted worker recovery.** `meal-ai-queue.service.ts` recovers abandoned `PROCESSING_AI` jobs after a 20-minute lease. `server.ts` waits for reminders during graceful shutdown but does not explicitly drain the AI worker. A process interruption during generation can therefore leave a visible delay until lease recovery. Immediate blanket resets would risk stealing a live job from another replica; this audit does not introduce that unsafe workaround. A worker drain and ownership-safe recovery require a separate tested change.
3. **AI requests share a connection budget.** `geminiLimiter` permits five requests per five minutes per IP. Multiple demonstration accounts behind one connection can collectively reach that intentional limit. Browsing already has verified-account keys; the AI budget was not loosened. Schedule demonstrations within the existing budget or design an account-scoped budget together with the global provider capacity controls.
4. **Simultaneous refresh in separate tabs.** The refresh guard is per JavaScript client, while browser cookies are shared. Two tabs can race a rotating refresh token; the rejected request's controller clears the cookie. This is a code-level concurrency risk, not a newly reproduced cross-tab browser failure. No replay allowance was added to the server. Cross-tab coordination should be tested before demonstrating the same account in several active tabs across token expiry. Different roles should use separate browser sessions.

## Verification

- Backend: **898 passed, zero failed, one existing TODO** (899 total), with `CLINICAL_CLARIFICATIONS_ENABLED=false` as the established suite baseline. The normal development API retains its existing enabled configuration.
- Frontend: **883 Vitest tests plus eight Node worker/dependency tests passed**. The final request-budget adapter and password-boundary tests were rerun after broadening authenticated mutation coverage: 13 passed.
- Backend and frontend builds and lint passed; architecture guard and all 25 entry-point budgets passed. Production build output stays separate from the running development server.
- Normal localhost API: registration and password reset reject overlong multibyte synthetic passwords before account writes. Unknown origins receive no credentialed CORS allowance. Readiness returns 200. The restarted frontend identifies Next.js 15.5.27 and its login route returns HTTP 200.
- Exact historical admin profile review and a newer clarification case return their saved snapshots. Sensitive-detail reads create access-audit events. Anonymous, member and RND requests to the admin case endpoint remain denied.
- Dependency audit after the patch: backend runtime zero findings; frontend runtime zero findings. Absence of advisories does not establish absence of vulnerabilities.

No shared migration, seed, import, real-account credential change or demo promotion was performed. Normal synthetic-account sign-ins and audited reads create their ordinary sessions/access events. Unrelated checkout edits were preserved. The local frontend was restarted to load the patched dependency.
