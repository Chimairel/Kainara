## Image protocol and data compatibility

`KAINARA_MEALS_V1` gains optional nullable `image`: `url`, `imageKind`, `altText`, `licenseCode`, optional creator/source/license URL. Existing image-free JSON remains accepted. Match the existing renderer and CSP allowlist rather than accepting links that the browser cannot display. Only direct HTTPS Cloudinary upload images, Panlasang upload photos and YouTube thumbnails are admitted; credentials/private/unsupported URLs fail preview validation. No remote image is fetched during preview or import, and no Cloudinary API call is made. Image existence or correspondence with a recipe is not established by a syntactically valid link.

Persist the URL in existing `adaptedImageUrl` with existing attribution fields. Keep representative/exact type and actual creator; do not manufacture Nutritionist authorship, known licensing, provider identities or dimensions. Unknown license is null with creator/source, matching existing source photography semantics. Linked-image updates/audits commit within the existing all-or-nothing batch transaction. Image-only changes cannot evade duplicate recipe signatures or overwrite an existing recipe. Export resolves supported current/source photography and includes valid image metadata without clinical/private records. New hashes normalize schema field order; exact legacy completed hashes are still checked without rewriting receipts.

Migration `20261017030000_batch_linked_meal_images` extends the existing image-dimensions constraint with an attributed URL-only state, retaining the original empty/uploaded states. A real local import initially caught that metadata-only rows violated the original constraint; add this migration instead of inventing Cloudinary dimensions. Null-valued incomplete linked attribution is rejected. Upload assignment clears an older linked URL so the actual upload can display; unassign removes a linked URL with its metadata. Existing legacy adapted recipes retain their prior presentation when no linked metadata exists.
