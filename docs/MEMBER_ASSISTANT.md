## Accepted design

- Member portal only. **Nara** reuses the existing Tanod mascot as the floating chat button and chat identity. The larger, transparent launcher has a subtle silhouette shadow and clears the mobile bottom navigation. Its accessible name is **Open Nara chat**. Hover or keyboard focus cycles through five friendly greeting tooltips and shows her open-mouth smile. Leaving, activating or dismissing the tooltip restores pointer tracking; returning focus after closing chat does not reopen the greeting or smile. Member bubbles and their current profile avatar sit on the right; Nara's bubbles and static portrait sit on the left.
- At desktop widths (1280 CSS pixels and above), a drawer starts at 420 px and overlays the workspace, flush with the right and bottom edges, without resizing the page. Drag its left edge or focus the resize separator and use Left/Right (24 px), Home (360 px) or End (up to 800 px, preserving 320 px of workspace). Width is retained in the authenticated layout across closing/reopening, without browser storage. Its top sits below the portal header, leaving the theme toggle and notification bell accessible; header menus stack above the assistant. It slides in from the right in 280 ms and closes in 180 ms, with immediate transitions for reduced motion. Closing content becomes inert during its exit. Smaller widths use a full-screen dialog with keyboard focus containment. The chat header and composer stay fixed while messages scroll.
- The closed launcher alone tracks the pointer. The open header faces front, loops upper left → front → upper right every 700 ms while awaiting a response, and uses the existing dizzy reaction while a request error or exhausted-credit confirmation is present. Retry, cancellation or New chat restore the appropriate state. Thinking pauses in hidden documents and remains front-facing for reduced motion; message portraits never track or animate. Artwork is decorative; text statuses and recovery controls remain accessible.
- KAINARA's current light/dark tokens, fonts, shared buttons and Solar icons are reused. No new dependencies, illustrations, vector database or duplicated food catalogue.
- The panel contains New chat, Close, free shortcuts, bounded conversation history, meal details, references, AI consent and recoverable errors. Closing/navigation preserve draft and conversation; a bounded account-keyed sessionStorage copy restores them after refresh. Sign-out/account changes abort pending browser requests and clear private saved chat. New chat clears context, never usage. The input uses a neutral rounded focus boundary without the former green inner-field highlight.
- Internal result links dismiss the covering dialog below 1280 CSS pixels so members can read the destination. Desktop navigation preserves the dock; both retain conversation state.

## Hybrid routing and credit consent

`GET /api/user/assistant` reports rollout status and the authenticated member's current allowance. `POST /api/user/assistant/messages` accepts a UUID request key, message (1000 characters maximum), optional fixed action, `allowAi` (false by default), and at most six context messages of 500 characters each. No caller-supplied owner, membership, tool names or arbitrary URLs are accepted.

Free shortcuts: About KAINARA, Find a meal (opens the search conversation), Today's nutrition, My nutrition guidance, and View my plan. Greetings, app instructions, credit FAQs and equivalent direct commands also return prepared system responses. **Free requests have no confirmation prompt and never call Gemini.**

Recognizable food-search, food-composition and nutrition-education requests first return an inline confirmation: **This request uses 1 AI credit**, current balance, Continue and Cancel. Unknown or ambiguous app-information requests return free topic choices instead. Preflight does not reserve a credit or call Gemini. Only explicit `allowAi: true` proceeds. Cancel does not create a receipt or call the provider. A completed-response retry is recovered before asking for another credit.

### Prepared system information

`backend/src/domain/member-assistant-information.ts` contains the versioned member guide and fixed internal destinations. It covers the app overview, current/target weight, health and personal settings, dietary preferences, outside-food logging instructions, water, theme, meal tracking/swaps/history/library, groceries, guidance, membership, exports and notifications. The matcher normalizes punctuation/contractions, uses action/topic aliases (including selected Tagalog/Bisaya wording), and corrects a small explicit list of common typos. This is bounded pattern matching, not unrestricted language understanding, an LLM, embeddings or vector retrieval. Unclear requests ask for clarification and offer topic links for free. Update this file and its phrase/destination tests when the corresponding screen or workflow changes.

Named destinations appear as colored, underlined inline links in replies. Mobile links dismiss the covering chat; desktop links preserve the drawer and conversation. These information replies run before usage preparation/reservation even if `allowAi` is supplied, work at zero credits, and create no assistant receipt or member-data change. There is no automated food log, profile update or other member mutation from chat.

### Browser answers and recent balance reuse

The member hook now resolves prepared help, greetings, credit explanations, the Find a meal introduction and plan navigation locally. Sending these messages makes **zero assistant message API calls**, with no per-question authentication, membership or credit query. An initial authenticated status request still checks feature availability and loads the allowance. Personalized shortcuts (today's recorded totals and saved guidance), food-search preflight and confirmed AI requests still use the existing authenticated API.

The backend guide remains the reviewed source. Run `node scripts/sync-assistant-guide.mjs` after editing it to regenerate the self-contained frontend module. `--check`, a frontend parity test and repository CI reject guide drift. No server-only imports, secrets or personal data enter this generated guide. This preserves independent backend/frontend deployment roots without adding a package or runtime cross-project import.

Credit display reuses its in-memory snapshot for 60 seconds and until the returned weekly reset, whichever is earlier. Concurrent refreshes share a pending GET. Opening chat or returning focus/visibility refreshes only when stale; there is no periodic chat polling. AI/preflight responses update the snapshot, failures force a refresh, and `kainara:membership-updated` invalidates it immediately. An open chat schedules a refresh at weekly reset. Slow older reads cannot overwrite a newer response or membership refresh. Credit state remains in the account-keyed authenticated layout and requests abort on unmount. Reload/sign-out ends the balance cache; balances and entitlements are never restored from chat storage.

The cached balance is display-only. Every confirmed AI request still passes current server-side membership/credit admission and locking. Other tabs or external membership changes can make the display briefly stale until the next refresh; they cannot authorize spending through the cached value. This change does not cache personalized guidance, nutrition totals, meal-search eligibility or other portal polling, and does not quantify total Neon savings.

## Data and safety boundaries

- Natural language is interpreted into a strict intent/filter schema. Existing code performs retrieval, eligibility and arithmetic. Supported recipe filters: name, meal type, included/excluded ingredient keywords, protein minimum, energy maximum, fat maximum. Ambiguous qualitative limits and other nutrient operators require clarification; no guessed numeric thresholds.
- Results use the existing compatible certified library query with its base verification, current profile, allergy, condition, flag and clearance gates. This first version searches that compatible library; the wider browse-only raw-source catalogue is still available in the existing Meal Library screen. AI cannot add a source meal or grant approval. Displayed recipe-serving nutrition excludes separately paired rice.
- Numeric recipe filters compare at the same one-decimal precision displayed in chat. Existing medical admission checks and stored measurements retain their authoritative values.
- Today's totals use owned, non-voided DONE logs and the existing nutrition eligibility predicate, with Asia/Manila day bounds. Missing logs are not inferred; incomplete entries are explicitly described as partial.
- Guidance comes from the member's acknowledged active planning report and preserves the current policy/safety revision checks. Direct guidance is free. AI explanations receive only bounded saved guidance and recent conversation; external source links come from saved references, never model-created citations.
- No chat action changes meals, logs, targets, profile or RND decisions. Links open existing screens. Clinical advice/diagnosis/clearance requests are outside scope.

## Persistence and abuse controls

Additive migration `20261015100000_member_assistant` adds the `MEMBER_ASSISTANT` usage operation and `AssistantRequest` receipts. Receipts contain owner, request key, payload digest, state, times and bounded result payload for retries. Full chat transcripts are not stored in this table. The browser's bounded recent-history copy is described below. Personalization is per authenticated request.

### Temporary refresh recovery

The authenticated member layout restores at most 40 recent messages, a 1000-character draft, panel-open state, unconfirmed consent and an interrupted paid request key from account-keyed **sessionStorage**. The versioned snapshot is bounded to 80,000 serialized characters and expires 24 hours after conversation creation, not on a sliding window. Read/write discards expired or invalid data; storage failure leaves chat usable in memory. New chat removes the saved history; sign-out, invalid authentication, explicit login, account deletion and account switching clear private saved chat. Browser tab restoration can retain sessionStorage, so expiration is enforced independently. No new database table or transcript sync is added. Restored replies show their original timestamp; they are historical answers, not current measurements or permissions.

Before sending a confirmed AI POST, the browser saves only its receipt key as active work, never persisted automatic consent. After refresh it makes one authenticated `GET /api/user/assistant/requests/:requestKey`, which checks the owned existing receipt and returns its state, original completion time and saved response when successful. It cannot reserve credits, write a receipt or invoke a provider. Running/unknown delivery offers **Check reply** without polling or automatic POST replay. A missing receipt is not proof that work never started, so it does not claim that no credit was spent. Failed/expired work can be sent again as a new, explicitly confirmed request. Duplicate completed replies are not appended twice.

### Food and nutrition scope

`FOOD_FACTS` retrieves up to six FNRI/USDA records using exact names/verified aliases first, then a bounded name lookup with whole-word validation. Ambiguous or truncated matches ask for a full name/source instead of inventing a selected food. Facts use recorded per-100-g composition, including available micronutrients, and never assume a piece weight. Missing values are omitted; zero is retained. Stable public composition lookups share the existing ten-minute invalidation-aware cache, capped at 64 terms; no member context or authorization is cached there.

`NUTRITION_QUESTION` uses a second bounded model call with curated WHO healthy-diet and FoodSafety.gov excerpts and code-selected source links. It is general education, not unrestricted web search. Unsupported details require an honest evidence limitation; the model is instructed not to invent numerical food facts, personal targets or clinical clearance. The same one-credit receipt covers interpretation and explanation; existing shared provider budgets still apply. Main facts stay compact, with additional recorded nutrients in an expandable section. No new dependencies, embeddings or food-data copy are introduced.

A PostgreSQL advisory transaction lock per member serializes admission across API instances. Active reservations consume available credits until completed, failed or expired (90 seconds). One active AI request per member and **one confirmed AI admission per rolling minute**, measured from admission start, including failed attempts. Receipt replay does not start a new cooldown. A separate 30 requests/minute route limiter bounds direct/preflight traffic, in addition to the existing API limiter. Request keys bind to the payload and authenticated owner; changed-payload reuse is rejected. Status and response allowances include the current `nextAiRequestAt`; admission rejections include `retryAt` and `Retry-After`. The browser counts down locally, keeps free help available, preserves blocked drafts and never sends automatically when the timer expires. New chat and refresh do not reset the server limit.

Receipts older than eight days are removed on the member's next AI admission and by the daily check-in cron while the feature is enabled. Operate that existing cron to enforce cleanup for inactive users. Export includes retained receipts when enabled; account deletion cascades them. Disabling the rollout pauses its cron cleanup too; purge retained receipts before a prolonged shutdown if required.

Each provider call passes through existing project-wide capacity admission. Chat additionally defaults to **20 provider attempts per rolling 24 hours**, capped so **20 project requests remain outside chat** under the default 40-request project limit. An oversized chat override cannot spend the core reserve. Member credits do not guarantee immediate provider capacity. Each model call has a single attempt, the existing 15-second provider timeout and an explicit output-token ceiling; no hidden fallback cascade or automatic browser retry. At most two calls per assistant request.

## Rollout

1. Review/apply the additive migration to a confirmed target, using `prisma migrate deploy`; regenerate Prisma clients for all API/worker instances. Do not use `db push`.
2. Deploy the compatible code with the assistant disabled, then enable after all readers support the new enum value. Default: disabled. Existing portals continue operating without the new table when disabled.
3. Set `MEMBER_ASSISTANT_ENABLED=true`. Optional settings:
   - `MEMBER_ASSISTANT_FREE_WEEKLY_CREDITS=5`
   - `MEMBER_ASSISTANT_LIFESTYLE_WEEKLY_CREDITS=15`
   - `MEMBER_ASSISTANT_HEALTH_WEEKLY_CREDITS=30`
   - `MEMBER_ASSISTANT_PROJECT_RPD=20`
   - `MEMBER_ASSISTANT_CORE_RESERVE_RPD=20`
4. Verify normal member login, free action without consent, AI consent/cancel, one confirmed response, idempotent retry, current membership allowance and cleanup scheduling. Existing Gemini credentials/capacity configuration apply.

This feature branch has not applied its migration to Neon, changed hosted secrets, or deployed the assistant. Isolated tests use synthetic data and stubbed provider responses; these do not establish real-model language quality or clinical validation.
